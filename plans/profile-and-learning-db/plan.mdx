> 📍 現況（2026-06-25）：🟢 後端核心完成。P1–P4 學習迴圈（關鍵字權重學習 TF 詞頻比較、極性推導、append-only KeywordWeightRevision、self_evolve 閘 ≥50 consent 樣本）已實作並有測試；三分判斷即時學習＋決策回顧端點已上。語意檢索待向量灌入。最新進度以 docs/governance/05-進度與白話術語.md 進度表為準。

這份計畫把三件事併成一條連貫的路：**白名單登入 → 個人資料管理 → 把使用者身分綁進後端學習庫**。對使用者來說，登入後會多出一頁「個人設定」，能看到自己的帳戶、調整「是否把行為分享給團隊」、檢視 AI 從自己行為學到的偏好；對系統來說，從此每一筆收藏／評分／註記都帶著**具名的白名單帳號**，餵進兩條學習線——團隊共享的 `keyword_weights`，以及每人專屬的個人化偏好。

上方畫布是四個關鍵畫面（登入、個人設定、同意彈窗、白名單管理）。以下是技術計畫。

### 決策摘要

<Callout id="decision-core" tone="decision">

**三個已拍板的方向（本計畫據此設計）：**

1. **先 UI＋資料模型，認證延後**：Phase 1 只交付畫面與資料表結構；密碼／SSO／session 保護放到 **Phase 2**。Phase 1 沿用現行 `HQadmin` 佔位帳號，不阻斷既有流程。
2. **兩段式同意**：第 1 段由**管理員開通白名單**（界定合作範圍），第 2 段由**本人在個人設定自行同意**共享。兩段都成立，行為才會具名匯入團隊共享庫。
3. **雙軌學習都要**：同時建「團隊共享知識庫」與「每人個人化偏好輪廓」。團隊線沿用既有 `keyword_weights`，個人線新增專屬資料表。

**實作層級也已確認（原 Open Questions，已拍板）：**

- **權重儲存**：個人線採**新增 `user_keyword_weights` 表**（`user_id + term` 複合主鍵），既有 `keyword_weights` 與 revisions 管線不動。
- **同意範圍**：同意**只 gate「匯入團隊共享庫」**；個人化（只用本人資料、只服務本人）免同意即可運作。
- **撤回處理**：撤回**只停止後續匯入、不回溯重算**已聚合的去識別化權重。

</Callout>

### 使用者會看到什麼

David（@hqdesign.tw、已被管理員開通）在登入頁輸入公司信箱進入系統。第一次他在「個人設定」看到一張**共享同意**卡片，點開彈窗讀完範圍說明後按「同意並加入」——從這一刻起，他的收藏與評分會以「David」具名進入團隊庫。即使他**不同意**，AI 仍會在「我的偏好輪廓」卡片裡，用他自己的行為替他做個人化推薦（這條線只用他自己的資料，不外流）。

管理員 Aaron 在「白名單管理」頁開通／停用同事帳號，但他**看不到、也不能代勾**任何人的共享同意——同意永遠是本人的動作。

雙軌學習落在兩張表：團隊線**沿用既有 `keyword_weights`**（全域聚合權重，連同 `keyword_weight_revisions` 修訂鏈一起保留，不動既有學習管線）；個人線**新增 `user_keyword_weights`**（以 `user_id + term` 為複合主鍵）。這樣個人權重與團隊權重彼此獨立、互不污染。`preference_profiles` 則存較高層的個人化輪廓（重點／避免關鍵字、偏好類別、預算區間），直接餵畫面上的「我的偏好輪廓」卡片。`users` 擴充三欄承載白名單與同意狀態（皆預設 `false`，既有資料回填亦為 `false`，保守起見不預先開通、不預先視為已同意）。

**寫入路徑（讀寫分離）**：`user_keyword_weights` 與 `preference_profiles` 都是**衍生表**，由 `app/jobs/learn_keywords.py` 擴充的 per-user 聚合計算後寫入（個人線只吃本人 `events`）；`GET /api/v1/me/preference-profile` 等 API **只讀不算**。亦即本計畫除了讀取端點，還需在學習任務裡新增個人線的計算邏輯，否則表會是空的。

### 風險與緩解

<Callout id="risks" tone="risk">

- **Phase 1 沒有真認證、`user_id` 可偽造**：`resolve_user_id()` 不驗證 body 帶入的 `user_id`，呼叫端可冒名（見上「行為寫入」段）。緩解：整支 API 目前已在 `app/main.py` 掛 `Depends(require_api_key)`，Phase 1 限本機／白名單環境使用；`/api/v1/admin/*` 與 `/api/v1/me/consent` 先加暫時性 header 檢查並標記 TODO；**Phase 2 改由伺服器端 session 推導 `user_id` 與 role，忽略 body 值**。
- **同意門檻不能只在前端，否則行為仍可能未經同意入庫**：團隊聚合須在**伺服器端**過濾。緩解：在 `app/jobs/learn_keywords.py` 的團隊聚合加一道 **consent-aware join**——只納入 `whitelist_active && consent_shared` 的使用者行為。這是**真實新增工作**（既有聚合對全體 events 一視同仁，不分同意），非單純設定旗標。
- **撤回的回溯**：已聚合進 `keyword_weights` 的去識別化權重難以單點移除。**已拍板**：撤回只停止後續匯入、不回溯重算；既有原始 `events` 保留但自撤回時點起不再納入團隊聚合（consent-aware join 以當下 `consent_shared` 為準）。
- **複合主鍵 user_id + term**：避免 NULL 進主鍵的問題（這也是不在 keyword_weights 加 nullable user_id 的原因），但需確認 Alembic 與既有查詢相容。
