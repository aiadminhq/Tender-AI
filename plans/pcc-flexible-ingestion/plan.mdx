# PCC 彈性搜尋、多 transport 抓取與現有資料庫注入計畫

目標是把政府電子採購網（PCC）的搜尋條件從硬編碼改為可重用的 typed criteria，先以「**履約地點為台北市／新北市、預算不超過 5,000 萬、截止日距 Asia/Taipei 今日 1–10 天**」作為預設 profile，再把命中標案冪等寫入既有 PostgreSQL Corpus。列表沿用 HTTP adapter；詳情新增 Playwright persistent context、CDP attach 與 OpenCLI 診斷備案，但所有 transport 最終都回到既有 `FetchResult` → `detail_parser` → revision-first DB 流程，不建立第二套 parser 或資料 sink。

本計畫是核准門檻；核准前只新增此規劃文件，不修改後端原始碼或資料庫。

</RichText>

<Callout id="primary-decision" tone="decision">

**採用 `research_enrich` 作為唯一 live PCC → DB 主流程，但拆成兩階段並讓詳情 transport 可替換。** 第一階段從 PCC 列表直接解析名稱、機關、採購性質、預算、截止日與連結並 upsert `tenders`；第二階段透過 batch-scoped `DetailFetcher` 抓原始 HTML，再沿用既有 `is_captcha_page`／`parse_pcc_detail`、附件歸檔與 immutable revision。這可避免 CAPTCHA 讓核心列表資料無法入庫，也避免各備案各寫一套 parser。

</Callout>

<Callout id="current-window" tone="info">

以目前 Asia/Taipei 日期 **2026-06-22** 與建議預設「剩餘 1–10 天」計算，本次查詢截止區間為 **2026-06-23 至 2026-07-02（含首尾）**。執行時由本地時區動態計算，不把這組日期寫死。

</Callout>

<RichText id="transport-heading">

### 詳情抓取 transport 備案

列表查詢繼續使用目前 `_pcc_http.py` 的 `requests`／`SkipSSLAdapter`，因它速度快、可分頁且不需要真人狀態。只有詳情頁在 HTTP 回傳 CAPTCHA 時才切到 browser transport。所有 browser 路徑皆為**本機、headed、human-in-the-loop**：允許使用者手動完成 PCC 驗證後重用 session，但不實作 CAPTCHA 自動辨識、破解或 stealth 欺騙。

</RichText>

<Callout id="browser-security" tone="warning">

Browser profile 等同登入憑證：Playwright profile 固定放在 `tender-ai-backend/data/private/pcc-browser-profile/`（既有 gitignore 覆蓋）、目錄權限限本機使用者，禁止寫 log、commit、上傳或放入一般備份。CDP 只綁 `127.0.0.1`，啟動前檢查 `/json/version` 與 `/json/list`，禁止 ngrok／公開 reverse proxy，且不得關閉或接管非 PCC 分頁。不同 transport 不能同時持有同一 profile，需以 lock file 阻止重疊排程。

</Callout>

<Callout id="chrome-136" tone="risk">

**CDP 的「日常 Chrome default profile」假設需修正。** Chrome 136 起，remote debugging flags 對 default data directory 不再生效；必須指定非預設 `--user-data-dir`。因此備案實作為「專用 CDP profile」或經驗證可用的 Comet CDP session，而不是承諾直接附著一般 Chrome default profile。參考 [Chrome remote debugging 安全變更](https://developer.chrome.com/blog/remote-debugging-port) 與 [Playwright `connect_over_cdp`／`launch_persistent_context`](https://playwright.dev/python/docs/api/class-browsertype)。

</Callout>

<RichText id="spike-heading">

### 最小 Playwright spike（先做、通過才整合）

Spike 只處理一個已知 `case_pk`：啟動 headed persistent context → 導向 `PCCAdapter.detail_url(case_pk)` → 若出現 CAPTCHA，由人手動完成 → 取得 `page.content()` → 呼叫既有 `is_captcha_page` 與 `parse_pcc_detail`。**不連 DB、不下載附件、不跑整批、不改 parser。** 成功條件是同一 profile 關閉後重開，第二次能在無重新驗證或可接受的人工作業下取得正常 DOM，且 parser 解析出 case 名稱、預算／截止或既有 fixture 對應的關鍵欄位。

<RichText id="opencli-heading">

### OpenCLI 的合理角色

OpenCLI 不先包成 production fetcher。第一階段用 `opencli doctor` 驗證 Browser Bridge／CDP，用 `opencli cascade <PCC URL>` 與 `opencli explore <PCC URL> --goal ...` 判斷是否存在比 DOM 自動化更穩定的同源 request，再以 `opencli record` 在真人操作期間記錄 network candidate。只有當它能穩定輸出**未改寫的 raw HTML 或與 `ParsedDetail` 等價且可測的明確 contract**，才新增 PCC adapter；目前 `opencli web read` 只輸出 Markdown，不能餵給 `detail_parser`，因此僅作診斷與 selector/network 研究工具。版本先鎖目前已驗證的 `1.7.3`，不在本任務順手升級至 `1.8.4`。

</RichText>

<RichText id="implementation-heading">

### 實作工作包

0. **先完成單案 Playwright spike。** 新增本機-only `scripts/spike_pcc_playwright.py` 與 optional `browser` dependency；以專用 profile、headed 模式跑通「人工驗證 → page.content → 既有 parser」。S1–S5 未全過前，不修改 production transport 選擇、不掛排程。
1. **建立 typed criteria 與日期／金額正規化。** 在 `app/adapters/pcc.py` 定義 `PCCSearchCriteria`、`PCCListItem` 與驗證規則；`research_enrich.py` 的 argparse 只負責轉成 criteria。以 `ZoneInfo("Asia/Taipei")` 決定今日，拒絕負數、min > max、未知縣市與未知類別，錯誤訊息不得帶 DB URL。
2. **重構 advanced query 與完整分頁。** 用結構化 params 取代 `_ADVANCED_QUERY` 字串：`dateType=isSpdt`、`spdtStartDate/spdtEndDate`、`tenderRange=TENDER_RANGE_ALL`、預算與履約地點依 criteria 注入。解析總筆數／下一頁連結，逐頁抓取並以「新 case_pk 數」防無限迴圈。
3. **列表解析先成為可靠資料源。** 新增 `parse_list_items`，抽出 case_pk、name、org、category、tender_method、budget_wan、deadline_roc／iso、link；保留 `parse_list_case_pks` 作相容 wrapper。沿用 `tender_daily.py` 已驗證的欄位位置概念，但以表頭／selector 防止固定 table index 漂移。
4. **兩階段冪等入庫。** `_discover` 改收 `PCCListItem`，用 `(source_id, case_pk)` upsert；新舊案都更新公開現值與 `last_seen`，不覆蓋非空詳情欄位為空。列表 transaction 完成後才跑現有 `_process_one`。`CrawlRun.notes` 記錄 criteria、查詢頁數、列表命中、去重數、入庫數、詳情 deferred／failed，並保存 `created_case_pks`／`updated_case_pks`，讓首批復原範圍可被稽核而不是靠時間猜測。
5. **抽出 batch-scoped async `DetailFetcher`。** 現有 job 已在 asyncio 內，不能直接混用 Playwright sync API；建立 async fetcher lifecycle，一個 run 只啟動一次 HTTP session／browser context。HTTP provider 以 `asyncio.to_thread` 包裝目前同步 `PCCAdapter.fetch_detail`，Playwright／CDP provider 使用 async API，File provider 從 manifest 指定的 raw HTML 讀取，全部回傳既有 `FetchResult`。Browser provider 以 `page.goto` 的 Response 保留 status/content-type，再於人工驗證完成後取 `page.content()` 與 `extract_source_revision_key`。`_process_one` 改為 `await fetcher.fetch_detail(case_pk)`，parser 與 transaction 不動。
6. **整合 Playwright、CDP 與 file replay，但不做靜默接管。** CLI 增加 `--detail-transport http|playwright|cdp|file` 與明確 `--fallback-transport`；預設仍是 `http`。只有使用者配置 fallback 時，HTTP CAPTCHA 才對同一 case 重試一次 browser transport。CDP preflight 必須驗證 localhost endpoint、PCC target 與專用 profile，不得任意操作其他 tabs；file mode 必須同時提供 `--detail-html-dir` 與 case_pk manifest。
7. **保留 OpenCLI 診斷腳本。** 新增只讀 `scripts/probe_pcc_opencli.py` 或等價 wrapper，依序執行 `doctor`／`cascade`／`record` 並保存到 `data/private/pcc-opencli/`；不把 Markdown 當 raw HTML、不直接呼叫 DB。若未來產生 PCC adapter，另開工作包審核輸出 contract 與版本 pin。
8. **加入安全 dry-run。** `--dry-run` 可連 PCC 列表、跑完整分頁與本地驗證，但不建立 Source／Tender／CrawlRun、不抓詳情；`--detail-dry-run` 則只處理指定單案、禁止 DB／附件寫入。正式模式才寫 DB。
9. **驗證後執行一次正式注入。** 先確認 Alembic `head`、備份現有 DB，再 dry-run；人工抽查至少 5 筆 PCC 原頁的履約地點／預算／截止日，通過後正式執行並用 SQL/API 驗證總數、邊界與重跑冪等。排程不與第一批資料綁死；只有 Playwright S4 通過才允許 browser fallback 無人排程，否則固定為 operator-assisted。

</RichText>

<RichText id="rollback-heading">

### 上線與復原

第一輪先手動執行，不直接掛排程。正式注入前保留 DB backup 與 `CrawlRun.id`；若解析契約錯誤，以該 run 的 criteria／時間與新建 case_pk 清單產生 rollback 清單，人工確認後只刪除本 run 新建且沒有 Layer B 關聯的 Tender。既有 Tender 的公開現值更新不可用整庫 rollback 粗暴覆蓋，應由重新抓取或 backup 比對恢復。首輪成功後，才把完全相同的 CLI 參數放到 DB 同主機的 cron／launchd。Browser transport 必須與 DB job 同機、具 GUI session 與 profile lock；雲端／CI 只跑 mocks 和 fixtures。若 persistent session 每次仍需 CAPTCHA，排程只做列表入庫，詳情固定改為操作員手動批次，不以重試迴圈施壓 PCC。

</RichText>
