這套助手的「大腦」其實已經接通：使用者在右側問問題，後端會同時跑兩條檢索（標案 SQL＋語意＋相似案、知識庫向量＋關鍵字 RRF），把命中的證據塞進一段 grounding system prompt，再用 Ollama 串流回答；Ollama 不可用時自動退回模板，HTTP 仍是 200。前端則以 NDJSON 逐段累積、把 `delta.text`（累積全文）直接 replace 到最後一則 assistant，並把證據渲染成可點擊的來源卡。

換句話說，「LLM 當資料／知識庫助手」這件事已經能動。本計畫要補的，是讓它**好用且越用越貼近使用者**的四個真實缺口：① 首次引導（onboarding，新人不知道它在、能幹嘛）、② 全屏「指揮中心工作台」（重度使用時的第三形態）、③ 情境感知（助手讀得到你正在看的標案）、④ 對話留存（refresh 不再清空）。其中有兩、三個決策一旦上線就難以回頭（情境傳輸格式、對話留存的公開 id、Layer B 邊界），會在下方先定調。

<Callout id="decision-shape" tone="decision">

**已定調**：全屏形態＝「指揮中心工作台」——左側對話、右側情境工作區（當前標案的可行性、證據來源與快速動作）。
**開發優先序＝ 3 > 2 > 1 > 4**：先做①首次引導，再做②全屏，接著③情境感知接線，最後④對話留存。
情境感知（③）雖排第三，但全屏工作區與「針對這案」的引導都需要一小片唯讀的 `tender_id` 情境，因此建議把**最小情境切片**提前隨 Phase 1–2 落地（見下方 Open Questions），主軸仍維持 3 > 2 > 1 > 4。

</Callout>

## 四個真正的開發缺口

### ① 首次引導（onboarding）— 全新

目前完全沒有 onboarding：新人進站不知道右下角有助手、也不知道它能讀標案。Phase 1 以半透明遮罩 + 聚光圈點亮既有啟動鈕，搭配 coach-mark 分步解說；不使用 framer-motion，沿用專案既有的 tailwind animate。首次完成後寫入 `localStorage` 旗標（沿用 `assistant-window.tsx` 既有的 `saveMode`／`loadMode` 寫法），之後不再自動跳出。

### ② 全屏指揮中心 — 擴充既有形態

`AssistantMode` 目前只有 `sidebar | float`，需要新增 `fullscreen`。可重用既有 portal、`MODE_STORAGE_KEY` 持久化，連 `Maximize2` icon 都已 import；新增的是左對話／右情境工作區的版面與第三段切換按鈕。

右側情境工作區**不是新後端**：可行性估算與理由重用 `GET /api/v1/tenders/{id}/reasoning`（reasoning.py），標案明細重用 `GET /api/v1/tenders/{id}`（tenders.py），相似案重用 `GET /api/v1/search/similar/{id}`（search.py），承接／略過／轉發就近呼叫既有 `behavior.py` 的 `accept`／`save`／`share`。沒有當前 `tender_id`（③ 尚未接線或不在標案頁）時，右欄落到空狀態而非空殼——因此這一欄要能動，依賴最小情境切片先到位（見 Open Questions 的 `q-context-slice`）。

## 情境傳輸格式（難以回頭的決策）

情境物件一旦由前端送出、被後端與行為記錄消費，改 key 就會同時打到兩端與已存的 Layer B 事件。先把形狀定下來，第一版只放唯讀、最小欄位：

<Endpoint
  id="chat-context-endpoint"
  method="POST"
  path="/api/v1/assistant/chat"
  summary="對話串流，新增 context 與 thread_id"
  request={{
    "contentType": "application/json",
    "example": "{\n  \"messages\": [{ \"role\": \"user\", \"content\": [{ \"type\": \"text\", \"text\": \"這案我們適合投嗎？\" }] }],\n  \"thread_id\": \"thr_8Qk2Lm9vXp4t\",\n  \"context\": {\n    \"route\": \"/tenders/:id\",\n    \"tender_id\": 4821,\n    \"lang\": \"zh-Hant\"\n  }\n}"
  }}
  responses={[
    {
      "status": "200",
      "description": "NDJSON 串流：meta → delta（累積全文）→ done",
      "example": "{\"type\":\"meta\",\"scope\":\"tender_sql + semantic_search + knowledge_base\",\"sources\":[...]}"
    }
  ]}
>

`context` 與 `thread_id` 皆為選填，schema（`AssistantChatRequest`，`extra="allow"`）已能接收，未來要加欄位（例如「只在我看得到的清單裡找」）不會破壞既有呼叫。第一版只放 `route／tender_id／lang` 三個唯讀欄位，後端只消費 `tender_id`。`tender_id` 在線上是整數主鍵（範例 `4821`）；UI 顯示的案號 `#115-0621-01` 是另一個展示欄位，兩者不混用。`context` 隨當前路由即時重算——只有「新的一次提問」才帶上當下的 `context`，不會回頭改寫或中斷進行中的串流。

</Endpoint>

## 對話留存資料模型（難以回頭的決策）

**身分軸對齊既有 Layer B**：`owner_user_id` 採 `int FK → users.id`，與既有全部 Layer B 表（`events`／`tender_user_state`／`annotations`…）同一身分軸，具名透過 join `users.name／email` 取得，**不**在 thread 表另存帳號字串。現況 demo 尚無登入，寫入會落到 `name="default"` 的單一使用者（見 `services/behavior.py` `resolve_user_id`）——這也是下方治理段與 Open Questions 的關鍵前提。

`assistant_threads.public_id` 是對外可見字串，一旦被分享或寫進事件就難以更換命名法；採不可猜的 id（nanoid/base62 ≥ 12 字元，加 unique 約束），不採可枚舉的短序號。

**與既有 `events` 的關係（避免雙寫）**：`assistant_messages` 為對話全文的單一真相來源（逐則 `content`＋`sources`）；既有 `events`（已記 `type=search` 的提問、`click_link` 的點來源）維持輕量埋點，不重複保存全文。去識別化管線以 `assistant_messages` 為準，`events` 僅供行為計數。

## 資料三層與共享邊界

<Callout id="governance-callout" tone="warning">

對話內容與「點了哪個來源、問了什麼」屬 **Layer B（行為與想法）**。共享邊界＝**白名單（原則上 @hqdesign.tw、由管理者開通）內共享、依登入帳號具名、對外永不揭露**，且須**已取得本人同意**。對外發佈／匯出一律去識別化，行為資料不進公開版控與 GitHub Pages 對外視圖。預設**不**把對話自動納入共享學習，僅在明確同意後依所選機制納入（見 Open Questions）。

**現況前提（重要）**：demo 尚未有登入，`resolve_user_id` 會把所有寫入落到 `name="default"` 的單一使用者。也就是說，「依登入帳號具名共享」在登入落地前**還不成立**——Phase 4 的留存可以先做，但「具名」與「共享學習」必須等帳號身分到位後才開（見 Open Questions 的 `q-owner-login`）。

</Callout>

<Callout id="grounding-risk-callout" tone="risk">

**回答仍維持 Layer-A-only**：`_GROUNDING_SYSTEM` 要求回答只根據候選標案清單＋知識庫片段、嚴禁虛構清單外標案、一律繁體中文。加入 `context` 只是改變「檢索哪些候選」，**不可**把 Layer B 行為明細灌進回答或證據卡。
**雲端環境連不到 Ollama／PCC**：情境接線與 grounding 來源正確性需在能連線的本地環境驗證；雲端只跑得了不依賴 LLM 的單元測試與型別檢查。

</Callout>
