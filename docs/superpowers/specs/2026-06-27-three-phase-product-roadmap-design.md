# 三階段產品路線圖（Three-Phase Product Roadmap）

> 日期：2026-06-27
> 狀態：設計定案（brainstorming 通過，待 writing-plans 拆第一個可動工子專案）
> 範圍：產品層級路線圖。定義 Phase 1→3 的價值階梯、資料層演進、Phase 2 元件拆解與 Phase 3 天花板。**本檔為「方向與邊界」**，各子專案另立 spec → plan → 實作。

---

## 0. 一句話

Tender AI 沿「**選對案 → 備好標 → 送得出**」一條價值階梯演進；每一階都複用前一階的資料與學習，而非平行的三個產品。

| 階段               | 一句話                                 | 入口             | 出口                 |
| ------------------ | -------------------------------------- | ---------------- | -------------------- |
| **Phase 1 選對案** | 挑案＋推播＋習慣學習（現況，幾近完成） | 每日標案配發     | **「承接」**這個動作 |
| **Phase 2 備好標** | 承接後，輔助把投標基礎資料備到 60–80%  | 承接觸發         | **「備標工作包」**   |
| **Phase 3 送得出** | 人機協作把工作包填進投標網站           | 一鍵啟動上傳助手 | 人按下**最後送出**   |

**關鍵接點**：Phase 1 既有的「承接」動作（David 決定投入備標）正是 Phase 2 的**觸發器**。三階段是一條流水線，不是三個獨立系統。

---

## 1. Phase 1：選對案（現況＝收尾驗收，非重建）

對應 PRD §10 的 P1–P5（資料層 → 行為埋點 → RAG → 小助手 → 學習迴圈＋可行性排序）。**幾近完成**，定位為「收尾」：

- 待補：PCC／本機 Ollama／向量連線在能連線環境的實機驗證（§13.5 已列）。
- 待補：`category` 約 79% NULL 的回填（`app/jobs/backfill_category.py`，offline／冪等），這是學習與 Phase 2 類型分類器的共同天花板。
- 學習迴圈鐵則延續：正向權重可自動學；**負分一律人工**（owner 親自 ✗ 即時學習為唯一例外）。

> Phase 1 不在本路線圖重新設計，只標記其 backlog 為 Phase 2 的前置依賴。

## 2. 新增資料層：Layer D — 公司知識庫

現有三層（A 公開標案／B 行為／C 學出的知識）不足以「備標」。Phase 2 起新增**第四層**：

- **Layer D — 公司資產／知識庫**：統編、地址、負責人、財務、人力、**證照（含有效期）**、**過往實績**、**可重用文案片段（含 embedding）**、**原始投標文件資產庫**、**文件範本**。
- **起步方式**：匯入過往投標文件（PDF/Word）→ 抽取 → 結構化建庫；缺欄位由人補，之後隨每次投標滾動累積。
- **紅線（比 Layer B 更嚴）**：Layer D 與所有備標產出含報價、策略、實績，屬**公司機密**。**永不外流、永不進公開 repo／GitHub Pages**，不納入對外去識別化視圖。需寫進 `docs/governance/04-訓練資料規範.md`。

### 資料四層速記

| 層    | 白話                         | 揭露邊界                                                  |
| ----- | ---------------------------- | --------------------------------------------------------- |
| A     | 公開標案資料                 | 可公開、可從原始 HTML 重建                                |
| B     | 同事行為與想法               | 白名單(@hqdesign.tw)內共享＋具名、對外永不揭露（需同意）  |
| C     | 學出的知識（向量/權重/理由） | 衍生物可重算；對外去識別化                                |
| **D** | **公司資產／投標素材**       | **公司機密；白名單內使用、對外永不揭露、永不進公開 repo** |

## 3. Phase 2：備好標 — 共用地基 ＋ 四元件

### 3.1 共用地基（兩個引擎）

1. **公司知識庫（Layer D）**：如 §2。
2. **標案需求抽取器（Requirement Extractor）**：把承接案的**招標文件（可下載 ODT/PDF）**＋詳情頁，抽成結構化「需求 schema」：資格條件、押標金、履約期限、**必繳文件清單**、評選項目、規格。
   - ⚠️ **約束**：PCC 詳情頁有常駐型 CAPTCHA，無法全自動抓。**優先吃可下載的招標文件**；詳情頁走瀏覽器互動式補抓（沿用 PRD 既有「需登入資料源」的 Playwright persistent-context 架構）。

### 3.2 四元件（建在地基上，按上線順序）

| 代號   | 元件                 | 需求對應             | 風險／信任                     | 上線序   |
| ------ | -------------------- | -------------------- | ------------------------------ | -------- |
| **C3** | 資格文件備齊清單     | 資格文件備齊清單     | 低（決定性比對）               | **先上** |
| **C1** | 制式表單欄位回填     | 制式表單欄位回填     | 低～中（信心分數，低信心交人） | 次之     |
| **C4** | 規格拆解比對         | 標案規格拆解比對     | 中（複用相似案／向量）         | 並行     |
| **C2** | 服務建議書／文案生成 | 服務建議書／文案撰寫 | 高（生成，必人工潤飾）         | 最後     |

- **C3 資格清單**：抽取器 → 必繳文件清單 → 比對 Layer D 文件庫 → 輸出 ✓有／✗缺／⚠過期，每項連到實際檔案。最低風險、最快見效。
- **C1 欄位回填**：標案表單欄位 ↔ Layer D 欄位映射 → 產出已填表單（廠商資料表／聲明書／標單），每格附**信心分數**，低信心標紅交人。
- **C4 規格拆解比對**：抽取本案需求 vs 過往已投案／範本 → 標出**新增/特殊**要求，複用 Phase 1 既有相似案／向量基建。
- **C2 文案生成**：Claude API 依 Layer D ＋ 本案規格 ＋ 過往得標文案（RAG）生**草稿**，人潤飾；人的修訂回灌成更好的 RAG 範例。

### 3.3 需求 (c)：自動判斷標案類型並主動提出

- **標案類型分類器**（室內裝修／營繕／設備／勞務…）決定「套哪組範本＋取哪段 KB＋適用哪份必繳文件 profile」，並主動提示「此類標案通常還需要 X／Y／Z」。
- **依賴**：品質取決於 `category` 完整度 → 與 §1 的 `backfill_category` 共用前置。

### 3.4 資料流

```
過往投標文件 ──ingest──▶ Layer D 公司知識庫
承接的新標案 ──抽取器──▶ 需求 schema
                          │
        ┌────────┬────────┼────────┬────────┐
       C3資格    C1回填   C4比對   C2文案
        └────────┴────────┼────────┴────────┘
                          ▼
                  「備標工作包」(bid_prep_package)
                          ▼
                   人審閱/編輯 ──回饋──▶ 改善映射與 RAG 範例
```

## 4. Phase 3：送得出 — 半自動人機協作上傳

- **工作包組裝器（Package Assembler）**：把審過的 Phase 2 產出，組成投標網站要的確切檔案集／電子領投標格式（命名、格式、附件包）。
- **Playwright 上傳助手（Upload Assistant）**：persistent context 自動導航電子領投標、填可填欄位、上傳附件；**遇 CAPTCHA／憑證簽章／最終送出即暫停交人**，人完成後續跑，全程留審計軌跡。
- **誠實天花板**：憑證簽章與送出**必須人為**。系統目標＝「除了按那一鍵，全部備妥」。

## 5. 資料模型增量（指引，非最終 schema）

- **Layer D**：`company_profile`、`company_credentials`(證照/有效期)、`past_projects`(實績)、`proposal_snippets`(可重用文案＋embedding)、`bid_documents`(原始文件資產 repo)、`document_templates`。
- **Phase 2 工作態**：`bid_prep_packages`(每個承接案一包)、`requirement_extractions`、`field_fill_results`、`eligibility_checklists`。
- **Phase 3**：`submission_runs`(上傳助手審計軌跡)。
