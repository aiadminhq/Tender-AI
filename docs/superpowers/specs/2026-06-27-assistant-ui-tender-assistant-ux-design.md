# assistant-ui 標案助手操作流程與 UX 設計

> 日期：2026-06-27  
> 範圍：僅前端 UX / flow 規劃，不串接後端、不定義 API，不改動資料模型。

## 0. 目標

把 `assistant-ui` 變成一個真正可用的「標案工作助手」，而不是單純聊天框。

這個助手要解決的不是「問答本身」，而是標案工作中最常見的三件事：

1. 快速理解一個標案到底在問什麼。
2. 用自然語言把散落在頁面上的資訊串起來。
3. 在不離開當前工作流的前提下，幫使用者做下一步決策。

本次規劃先假設：

- 暫時不串接後端實際回答。
- 先把 UI / UX 的骨架、狀態、導引與情境設計清楚。
- 之後才把資料來源、RAG、工具與串流接上。

## 1. 這個助手是誰在用

### 1.1 主要使用者

1. **標案判斷者**
   - 需要快速看出一案值不值得投。
   - 常問資格、預算、截止日、地點、類別、履約要求。
   - 最在意的是「這案子是不是現在就可以排除或保留」。

2. **標案研究者**
   - 需要比較相似案、看趨勢、找歷史案例。
   - 常問「有沒有類似案」、「之前做過嗎」、「跟某案差在哪」。

3. **團隊協作者**
   - 需要快速把資訊轉成可傳遞內容。
   - 常問「幫我整理給同事」、「幫我產一段摘要」、「幫我列重點」。

4. **新人或低頻使用者**
   - 不熟系統，不知道從哪裡問起。
   - 需要很強的引導與範例，而不是空白對話框。

### 1.2 使用情境

- 正在看某一筆標案詳情，想直接問「這案子有沒有資格風險」。
- 在列表頁看很多案子，想先篩掉不值得看的。
- 在 swarm / swipe / kanban 中看到一個案子，想確認是否值得保留。
- 想比較兩個標案的差異。
- 想把「為什麼推薦這案」講給同事聽。
- 想要查歷史相似案或規則來源。

## 2. 這個助手要回答的問題類型

### 2.1 事實型

這類問題要盡量短、精準、可直接採用。

- 這案子的截止日是什麼時候？
- 預算多少？
- 地點在哪裡？
- 是工程、財物還是勞務？
- 有沒有資格限制？
- 有沒有押標金、履約保證金？

### 2.2 判斷型

這類問題不是單純查資料，而是要幫使用者做比較與歸納。

- 這案子值得投嗎？
- 跟我們之前做過的案子像不像？
- 跟 A 案比，哪個風險比較低？
- 這案子現在先保留還是先排除？

### 2.3 探索型

這類問題通常發生在使用者還不確定自己要問什麼。

- 幫我看這案子有哪些要注意。
- 先幫我整理重點。
- 幫我找相似案。
- 幫我估一下這案子會不會適合我們。

### 2.4 協作型

這類問題是為了把資訊轉成行動。

- 幫我整理成可以貼給同事的摘要。
- 幫我寫一段判斷理由。
- 幫我列出下一步要查的資料。

## 3. 使用者真正的需求

目前這個助手的核心需求不是「聊天」，而是把工作縮短成更少的切換成本。

### 3.1 使用者最常缺的東西

- 不知道從哪裡開始問。
- 看得到頁面，但看不懂所有欄位的意義。
- 已經有資訊，但沒有整理成決策語言。
- 想知道「下一步該做什麼」，而不是多一段解釋。

### 3.2 助手應該補的洞

- 幫使用者把分散資訊整合成可行判斷。
- 幫使用者把「直覺」轉成可傳達的理由。
- 幫使用者在列表、詳情、相似案、規則設定之間快速跳轉。
- 幫新手建立問法模板。

## 4. 助手定位

這個 assistant 不應該被設計成一般聊天機器人。

更合理的定位是：

- **左欄是對話**
- **右欄是情境**
- **上方是當前任務標題**
- **底部是可快速發問的輸入區**

### 4.1 產品語意

它不是「我要跟 AI 聊天」。

它是：

- 我現在正在看這個標案。
- 我想快速知道這個標案怎麼判斷。
- 我想直接把這筆工作做完。

### 4.2 操作原則

- 助手永遠附著在當前工作情境，不要讓使用者想半天自己在哪。
- 助手要主動給可點的問題，不只給空白輸入框。
- 助手回答後，要自然接下一步，而不是停在結尾。
- 不要讓使用者在浮窗與整頁工作台之間理解成本太高。

## 5. 操作流程

### 5.1 首次進入

目標：讓使用者 10 秒內知道這個助手可以做什麼。

流程：

1. 右下角 FAB 出現。
2. 首訪時只用一次輕量 onboarding。
3. onboarding 用 3 到 4 個步驟說明：
   - 可以問標案問題。
   - 可以看相似案。
   - 可以直接帶著目前頁面的情境問。
   - 可以切到完整指揮中心。
4. 結束後自動開啟助手，讓使用者立刻看到內容不是空的。

### 5.2 從頁面中自然打開

使用者在列表、詳情、swipe、kanban、dashboard 都可能需要助手。

理想行為：

- FAB 永遠可見，但不壓迫主工作區。
- 使用者如果在選取文字，最好可以看到「傳送給 AI」。
- 打開後的第一句話應該帶上當前頁面情境。

### 5.3 在標案詳情頁使用

這是最重要的情境。

建議流程：

1. 使用者打開某一筆標案詳情。
2. 右欄顯示這筆案子的概況、可行性、相似案與快捷動作。
3. 使用者可直接點「幫我看這案子值不值得投」。
4. 助手回答時優先引用當前標案。
5. 若要深入，就直接點「看詳情」或「看相似案」。

### 5.4 在列表頁使用

此時助手的角色不是摘要單一案子，而是幫使用者縮小範圍。

常見動作：

- 幫我找預算高於某門檻的案子。
- 幫我從這些案子中找出最有潛力的 3 個。
- 幫我解釋目前篩選條件會留下哪些案。

### 5.5 在 swipe / decision 流程中使用

此時助手應該變成「決策加速器」。

常見動作：

- 這案子 pass 的理由怎麼寫比較清楚？
- 這案子跟前一個案子差在哪？
- 幫我找出適合記錄成負向關鍵字的候選。

### 5.6 在 kanban / 協作頁使用

此時助手的角色偏向工作協作。

常見動作：

- 幫我整理成給同事看的摘要。
- 幫我比較兩個待辦案。
- 幫我列下一步要找的資料。

## 6. UI / UX 具體優化方向

### 6.1 不要做成一般聊天框

這是第一優先。

如果介面看起來像普通聊天 app，使用者會預期：

- 一直輸入問題。
- 等一個長答案。
- 沒有任務導向。

但這個產品要的是：

- 直接幫助決策。
- 直接給下一步。
- 直接跟當前頁面綁定。

### 6.2 空態要像工作台，不像聊天視窗

空態建議包含：

- 一句清楚的定位說明。
- 3 到 5 個可直接點的建議問題。
- 1 個快速進入完整指揮中心的 CTA。
- 1 個「從目前頁面情境提問」的提示。

空態建議類型：

- 這案子值不值得投？
- 幫我比較相似案。
- 這案子的資格門檻是什麼？
- 先幫我整理重點。

### 6.3 建議問題要分層

不要只放一組泛用問題。

應該分成：

- **快速事實**
- **判斷比較**
- **下一步行動**

這樣新手才知道怎麼問，熟手也能直接點。

### 6.4 回答後要接 follow-up

每次回答結束後，下面要接三種追問：

- 再深一層的事實。
- 比較性的問題。
- 行動型問題。

例如：

- 幫我列履約 / 資格 / 押標金。
- 跟 B 案比較。
- 幫我整理成可貼給同事的重點。

### 6.5 來源區塊要可收合

答案下方如果有來源，不要直接堆滿整個面板。

建議：

- 預設只顯示筆數與來源類型圖示。
- 點開再列出詳細來源。
- 每則來源保留來源名稱、類別與跳轉動作。

這樣可以避免回答區被來源牆壓垮。

### 6.6 右欄情境要有明確目的

右欄不應只是重複左欄內容。

右欄應該固定提供：

- 當前標案概況。
- 可行性與風險感知。
- 相似案。
- 快速動作。

使用者要知道右欄的價值是「不用提問就能先看懂」。

### 6.7 開 / 關 / dock / undock 的語意要簡單

目前介面有浮窗與側邊欄兩種模式。

建議語意：

- **浮窗**：快速查、短問短答。
- **側邊欄**：長時間工作、要邊看邊問。

右上角按鈕最好直接說清楚：

- 切成側邊欄
- 切成浮窗
- 前往完整指揮中心

### 6.8 composer 要降低輸入門檻

輸入框旁邊應該有三種輔助：

- 可直接點的範例。
- 對目前標案的快捷問題。
- 對資料源的明確提示。

輸入框 placeholder 不要太空泛，最好是：

- 問我這案子的資格、預算、期限或相似案

### 6.9 要有明確的 loading / streaming / error 狀態

即使現在不接後端，也要先定義體驗。

需要的狀態：

- 等待中：顯示「正在整理來源」而不是轉圈圈而已。
- 串流中：顯示正在回覆，避免使用者重複送出。
- 失敗：告訴使用者能重試，並保留已輸入內容。
- 無結果：提示可換問法。

## 7. 使用者問題清單

### 7.1 常見問題

- 這案子值不值得投？
- 這案子的資格限制是什麼？
- 有沒有押標金 / 履約保證金？
- 截止日還有幾天？
- 跟哪些案子最像？
- 如果 pass，要怎麼寫理由？
- 這案子適合哪個團隊處理？
- 有沒有可能先保留、之後再看？

### 7.2 常見需求

- 快速過濾掉不適合的標案。
- 用人話整理條件。
- 比較多個標案。
- 幫忙寫判斷理由。
- 幫忙把案子摘要給同事。
- 幫忙從頁面上的選取文字直接發問。

### 7.3 高風險需求

以下情境要特別保守：

- 使用者想讓 AI 直接替他下決定。
- 使用者想把未確認資訊當作事實。
- 使用者希望自動寫入負向規則或團隊決策。

這些都應該保持 human-in-the-loop。

## 8. 建議的資訊架構

### 8.1 左欄

- 對話內容
- 問題輸入
- 建議追問
- 來源引用

### 8.2 右欄

- 當前標案概況
- 可行性 / 風險
- 類別與狀態
- 相似案
- 快捷動作

### 8.3 底部

- 輸入框
- 送出 / 停止
- 可選輔助操作

## 9. 視覺與互動風格

延續現有 Tender AI house style，不重做整站視覺。

建議維持：

- 中性底色 + 單一 signal accent。
- 圓角卡片。
- 柔和陰影。
- 以 icon 形狀區分類別，不靠多色標籤。
- 浮窗 / 側欄保持一致的字級、卡片密度與 spacing。

### 9.1 可以強化的地方

- 空態做得更像「工作台入口」。
- source chips 更像可操作證據卡，而不是附件列表。
- follow-up 問題做成更明確的行動提案。
- 右欄內容更像「情境摘要」，不是重複的 metadata。

## 10. 不接後台時仍可先驗證的事

即使先不串接後端，還是可以先驗證 UX。

### 10.1 可以先做的

- 空態與 onboarding 文案。
- 對話 shell 的層級與 spacing。
- command center / dock / undock 的可用性。
- 樣板問題的分類。
- 右欄情境資訊排版。
- loading / empty / error 的假狀態。

### 10.2 可以先模擬的資料

- 一筆標案的摘要卡。
- 三個相似案。
- 三種回答模板：
  - 事實型
  - 判斷型
  - 協作型

## 11. 建議的 MVP 流程

### MVP 1

只做 UI 與假資料：

- FAB 打開助手。
- 浮窗 / 側欄切換。
- 空態導引。
- 追問 chip。
- 來源區收合。

### MVP 2

加上情境面板的可理解性：

- 當前標案概況。
- 相似案列表。
- 快捷動作。

### MVP 3

加上行為導向 UX：

- 從選取文字送出提問。
- 從詳情頁直接問這筆案子。
- 從列表頁帶篩選條件提問。

## 12. 結論

assistant-ui 標案助手的關鍵不是「有沒有聊天功能」，而是能不能在使用者工作時，幫他更快完成這幾件事：

- 看懂一案。
- 比較一案。
- 判斷一案。
- 把判斷說清楚。

最好的 UX 不是讓人一直打字，而是讓人一眼知道：

- 現在看的是哪筆標案。
- 可以直接問什麼。
- 問完後下一步可以做什麼。

這份規劃的重點就是把助手從「聊天框」提升成「標案決策工作台」。
