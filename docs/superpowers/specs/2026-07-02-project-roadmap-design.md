## 3. 分類原則（四狀態）

活文件所有項目一律歸入四狀態之一。每個狀態有明確的**納入準則**與**退出準則**（何時可移到下一狀態），避免狀態長期失真。

| 狀態   | 記號 | 納入準則                             | 退出準則（移出條件）                                     |
| ------ | ---- | ------------------------------------ | -------------------------------------------------------- |
| 已完成 | ✅   | 產出已存在且已驗證（或已 commit）    | 不移出；僅在被推翻時降級並記錄理由                       |
| 進行中 | 🚧   | 已動工、有明確負責流程正在推進       | 完成 → ✅；卡住且無限期 → ⏸ 並記錄原因                   |
| 擱置中 | ⏸    | 有明確前置未解、或**人明確指示暫停** | **僅在人明確說「重啟 X」時**才可移出；agent 不得自行恢復 |
| 規劃中 | 🗓   | 已定方向、但等授權／等前置／未動工   | 前置解除且動工 → 🚧                                      |

**紅線**：⏸「擱置中」→ 任何其他狀態的轉移，**只能由人明確重啟**觸發。這條對應使用者對部署議題「這個議題先跳過」的指示。

## 4. 活文件章節骨架（`plan.mdx` 固定結構）

每次更新照這個固定順序填，不臨時增刪章節（要增刪先改本 spec §4）：

1. **狀態橫幅** `<Callout tone="decision">`：本次快照日期 ＋ 一句話現況。
2. **一句話現況**：專案此刻站在哪。
3. **四狀態總覽 `<Table>`**：每個狀態列出項目數與代表項，作為導覽。
4. **已完成 ✅ 明細**：條列 ＋ 佐證（commit／檔案）。
5. **進行中 🚧 明細**：條列 ＋ 對應子專案 spec/plan 連結。
6. **擱置中 ⏸ 專章**：把 `HANDOFF.md` 8 項逐條攤平，頂部放 `<Callout tone="risk">` 標明「僅記錄、不主動執行」。
7. **規劃中 🗓 明細**：含 Notion 整合（待授權）等。
8. **工具盤點 `<Table>`**：MCP／CLI／平台 → 用途 → 授權狀態（可用／待 OAuth／本機限定）。
9. **待處理小問題**：如 `NOTION_TOKEN` 建議輪替、`block-secrets.py` hook bug（僅記錄不修）。
10. **責任邊界 `<Diagram>`**（沿用既有 roadmap 慣例）：Layer A/B/C/D 與對外隔離。
11. **更新紀錄**：每次更新補一行「日期 — 誰把什麼從 X 移到 Y」。

---

## 5. 更新規則

- **每批工作後**：①把受影響項目移狀態 ②更新橫幅快照日期 ③在「更新紀錄」補一行。
- **擱置中的移動**：見 §3 紅線——只有人明確重啟才可移出 ⏸。
- **對外邊界**：本 roadmap 與活文件**不含** Layer B（同事行為）／Layer D（公司投標素材）機密內容；工具盤點只寫「能力與授權狀態」，**絕不寫祕密值**（token／密碼／連線字串一律以佔位或名稱代稱）。
- **單一事實來源**：部署細節仍以 `HANDOFF.md` 為準，活文件只做狀態鏡射與索引；產品方向仍以三階段 roadmap spec 為準。
