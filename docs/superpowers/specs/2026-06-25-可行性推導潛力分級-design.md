# 可行性推導潛力分級（高/中/低潛力 ← 自學可行性分數）

## 1. 背景與問題

目前清單的「高/中/低潛力」標籤來自**每日報表快照**（`DailyTender.tier`），那是 `tender_daily.py` 的
`PRIORITY_RULES` 一套寫死的啟發式，**不會隨團隊使用而變聰明**。

使用者要的是：

> 「潛力區域的標籤改為可行性的分數……這些可行性加權指數之後都會因為訓練數據而重新組構……
> 應該要有個公式可以算，會隨著越多使用 AI 越知道這分數怎麼打。」

也就是：**潛力分級（tier）應由一個「會自學的可行性分數」推導出來，分數背後是關鍵字／特徵加權公式，
門檻與權重都隨團隊資料重新組構。**

### 1.1 關鍵陷阱：系統內有「兩個可行性分數」，只有一個能用

| 分數                     | 出處                                                                                        | 性質                                                                                                                                       | 能否反推 tier                          |
| ------------------------ | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 清單 `feasibility_score` | `query.py` `_display_feasibility(tier, feas_raw)`＝`_TIER_BASE_FEAS[tier] + 關鍵字權重微調` | **錨定在報表 tier 上**                                                                                                                     | ❌ 循環（拿 tier 算分、再拿分定 tier） |
| 詳情 `criteria_fit`      | `reasoning.py` `explain_tender`                                                             | 由 `base_rate + 類別/地點/預算/關鍵字/行為` 累加；**不依賴報表 tier**（snapshot 只取 `days_left` 餵急迫性中性提示，`tier` 取出但未進 fit） | ✅ 可用                                |

> 已逐行確認：`explain_tender` 的 `fit` 累加（reasoning.py 行 417–595）完全沒有讀 `tier`；
> 因此用 `criteria_fit` 反推 tier **不構成循環**。

**結論：真正「自學的可行性分數」是 `criteria_fit`。** 設計必須以它為分數來源，**取代**那個錨定報表 tier 的循環分數。

### 1.2 尺度錯位：使用者說的「80/60」≠ `criteria_fit` 的 80/60

`criteria_fit` 經 `max(0.03,min(0.97,fit))*100` clamp 後集中在以 `base_rate`（約 50）為中心的窄帶，
`explain_tender` 既有結論帶是 **≥62 strong / ≥42 consider / <42 weak**（已對齊實際分佈）。
若照字面把門檻設在 80/60，幾乎所有標案會掉進「低潛力」，UX 崩壞。

**解法（使用者已選定「信心校準門檻」）**：把「80」重新詮釋為**信心目標 80%**，不是分數 80。
人設定信心目標（高潛力＝其中 ≥80% 實際可行；低潛力＝其中 ≥70% 實際不可行），
**由資料學出能達到該信心的分數切點**。Stage 1 先用既有 62/42 當種子，Stage 2 由信心校準收斂。

## 2. 設計目標與非目標

**目標**

- 清單/詳情的潛力標籤由**團隊線 `criteria_fit`** 推導（分帶 high/mid/low）。
- 分數隨關鍵字權重學習而自動變化（既有 SL2 迴圈已具備）。
- 分帶門檻**由資料學出**（信心校準），且隨團隊樣本成長重新組構。
- **全團隊一致**：所有人看到同一標案的 tier 相同（用 consent-aware 團隊線，非個人線）。
- 全程 **offline／idempotent／append-only**，可在雲端（連不到 PCC/Ollama）驗證。

**非目標（YAGNI）**

- 不做個人化 tier（個人線分數仍可在詳情頁呈現，但清單 tier 用團隊線）。
- 不在本期做「信心目標的 UI 設定頁」——先用 job 參數＋預設常數，UI 留待後續。
- 不重寫 `tender_daily.py` 的 `PRIORITY_RULES`；`priority` 旗標保留為覆寫（見 §5.3）。
- 不動爬蟲、不碰 embedding / semantic 檢索。

## 3. 鎖定的設計決策（來自使用者選擇）

1. **分數來源** ＝ 既有 `criteria_fit`（團隊線推理分），非清單那個循環分。
2. **門檻學法** ＝ **信心校準**：人設信心目標，資料學切點。
3. **一致性** ＝ **全團隊一致**（consent-aware 團隊線，`build_criteria_profile(user_id=None)`）。

## 4. 架構：兩階段推出

### 分數來源（兩階段共用）

團隊線 `criteria_fit` 是 **Python 逐案計算**（profile 訊號是 dict，非純 SQL），無法直接塞進清單 SQL 排序/分頁。
故**物化**：用離線 idempotent job 把每案的團隊線 `criteria_fit` 算出、存進 `Tender.feasibility_team` 欄位，
清單 SQL 再對「存好的整數欄」做分帶與排序。計分核心由 `reasoning.py` 抽成可重用純函式，
確保**詳情頁與批次物化用同一套公式、結果一致**。

### Stage 1（可獨立上線的最小單元）

`tier ← band(feasibility_team)`，門檻用**固定種子** `c_high=62 / c_low=42`（＝既有結論帶）。
`feasibility_team` 為 NULL（尚未計分）→ **回退報表 tier**。`priority` 報表旗標 → 覆寫保留（見 §5.3）。

### Stage 2（自學門檻）

新增 `learn_tier_thresholds` job＋`TierThresholdRevision` 表，用信心校準從 consent-aware 團隊線學 `c_high/c_low`，
append-only。串進 `self_evolve` 於 `learn_keywords` 之後。≥50 樣本閘＋護欄＋回退種子。
資料不足或校準異常 → 自動退回種子，故 Stage 2 不會讓 Stage 1 變差。

## 5. 後端變更

### 5.1 計分核心重構（reasoning.py，行為等價、純抽出）

把 `explain_tender` 內 fit 累加段抽成純函式，供 `explain_tender` 與批次 job 共用：

```python
def accumulate_fit(t, profile, positive_kws, manual_negatives, learned_negatives,
                   days_left=None) -> tuple[float, list, list]:
    """回傳 (fit_raw, weighted_reasons, neutral_reasons)；不做 clamp。"""
    # ← 原 explain_tender 行 415–595 整段搬入，邏輯不變

def finalize_criteria_fit(fit_raw: float) -> int:
    return round(max(0.03, min(0.97, fit_raw)) * 100)

def verdict_for(criteria_fit: int) -> tuple[str, str]:
    # ≥62 strong / ≥42 consider / <42 weak（原文案不變）

def compute_team_fit(t, profile, positive_kws, learned_negatives) -> int:
    """批次用：團隊線（manual_negatives=[]）→ 物化整數分。"""
    fit_raw, _, _ = accumulate_fit(t, profile, positive_kws, [], learned_negatives)
    return finalize_criteria_fit(fit_raw)
```

`explain_tender` 改為呼叫 `accumulate_fit` → `finalize_criteria_fit` → `verdict_for`，輸出與排序不變。
既有 `test_reasoning.py` 即為等價回歸護網。**不新增任何負權重邏輯**（符合 P4/P5「負分人工專屬」紅線：
門檻學習產生的是「分數切點」，不是 keyword 負權重）。

### 5.2 資料模型（models/tender.py、models/knowledge.py）

- `Tender.feasibility_team: Mapped[int | None]`（nullable Integer，0–100，物化團隊線分）。
- `TierThresholdRevision`（鏡像 `KeywordWeightRevision` 的 append-only 審計表）：
  `id` PK、`batch` String(32) indexed、`c_high` Integer、`c_low` Integer、
  `target_high` Float、`target_low` Float、`min_support` Integer、
  `support_high` Integer、`support_low` Integer、`feasible_samples` Integer、`infeasible_samples` Integer、
  `fallback` Boolean（是否因護欄退回種子）、`created_at` indexed。
- Alembic migration（chain from head **`a2d6f8c4b1e3`**）：`add_column` + `create_table` + index。

### 5.3 清單查詢接點（query.py）

- 新 `_band_tier_expr(score_col, c_high, c_low)`：
  `score≥c_high→'high'`、`≥c_low→'mid'`、`else→'low'`、`score IS NULL→NULL`。
- `tier` 投影改為：`coalesce(priority覆寫, band(feasibility_team), 報表tier回退)`
  - 報表 snapshot tier == `'priority'` → 直接用 `'priority'`（人/規則層級訊號，凌駕分數）。
  - 否則 `feasibility_team` 非 NULL → 用 `band()`。
  - `feasibility_team` 為 NULL → 回退報表 tier（冷啟動）。
- 清單 `feasibility_score` 改投影 `feasibility_team`（NULL 時回退既有 `_display_feasibility`，保證不為空）。
- `sort=feas` 改以 `feasibility_team desc nulls_last` 為主鍵、`days` 破題；`sort=tier` 沿用 `_tier_rank`（含 priority）。
- `c_high/c_low` 取得：每次查詢讀**最新一筆 `TierThresholdRevision`**（單列、indexed），無則用種子常數 62/42。
- 前端篩選的 tier enum（low/mid/high＋既有 priority）**不變** → Phase 1 的雙握把 slider 無需改碼。

### 5.4 物化 job（app/jobs/score_team_feasibility.py，新檔）

```
build_criteria_profile(session, user_id=None)   # 團隊線 profile，一次
load positive_kws / learned_negatives           # 各一次
for t in all tenders: t.feasibility_team = compute_team_fit(t, profile, kws, neg)
commit
```

offline／idempotent（同輸入同輸出）／無網路。初次需跑一次回填；之後由 self_evolve 觸發。

### 5.5 門檻學習 job（app/jobs/learn_tier_thresholds.py，新檔）— 信心校準數學

樣本＝consent-aware 團隊線（`whitelist_active && consent_shared`、結論 ∈ {可行,不可行}），
每筆取 (該案 `feasibility_team` 分數 s, 標籤 label)。

- `c_high` ＝ 滿足「`P(可行 | s≥c) ≥ target_high` 且 `count(s≥c) ≥ min_support`」的**最小** c（最大化高潛力覆蓋）。
- `c_low` ＝ 滿足「`P(不可行 | s<c) ≥ target_low` 且 `count(s<c) ≥ min_support`」的**最大** c。
- 預設 `target_high=0.80`、`target_low=0.70`、`min_support=10`、種子 `SEED_C_HIGH=62`、`SEED_C_LOW=42`。
- 演算法：對 unique 分數掃描候選切點，計條件精確率，O(n log n)、確定性。

**護欄（任一不滿足 → `fallback=True` 退回種子）**

- 必須 `c_low < c_high`（學出 c_low≥c_high 視為失敗）。
- 兩類樣本各 ≥ `min_support`。
- `c_high` clamp 至 [50,90]、`c_low` clamp 至 [20,55]。
- 任一切點 support 不足 → 該切點退種子。
- 寫 `TierThresholdRevision`（append-only，`batch=now.isoformat()`），記 support / samples / fallback。

> 限制（已知、可接受）：分數與門檻同源（in-sample 校準），早期樣本少時噪音大——故先用種子、≥50 閘、
> 護欄與 clamp 收斂；隨樣本成長門檻才逐步偏離種子。這正是「越用越知道分數怎麼打」。

### 5.6 自演化串接（app/jobs/self_evolve.py）

`run_self_evolution`：gate（≥50 consent-aware、且較上批有新增；`force` 可覆寫）→ 若 evolve：
`learn_keywords` → `score_team_feasibility`（用新權重重算分）→ `learn_tier_thresholds`（用新分＋標籤校準切點）。
三者皆 offline／idempotent，順序固定（分數須先於門檻校準）。

## 6. 前端影響（極小）

- Stage 1：**無需改碼**。tier enum 不變，slider 照舊；tier 值與 `feasibility_score` 自動反映團隊線。
- 可選（非阻擋）：tier 圖例/tooltip 文案改述「依可行性分數推導」，i18n zh/en 成對；House style 不變。

## 7. 測試計畫（鏡像 test_reasoning.py / test_self_evolve.py）

- **重構等價**：`accumulate_fit`/`finalize_criteria_fit` 對既有案例輸出與重構前一致（回歸）。
- **物化**：`compute_team_fit` ＝ `explain_tender(user_id=None)` 的 `criteria_fit`（同案同分）；job 冪等（連跑兩次值不變）。
- **分帶邊界**：s=62→high、61→mid、42→mid、41→low、NULL→回退報表 tier；priority 覆寫保留。
- **信心校準**：構造已知分佈，驗 `c_high/c_low` 落在預期；目標調高→切點上移。
- **護欄回退**：樣本不足／單類／c_low≥c_high／超出 clamp → `fallback=True` 且用種子。
- **consent-aware 母體**：非白名單/未同意/結論非{可行,不可行}不納入；與閘計數準則一致。
- **append-only**：多批次只新增 revision，不就地覆蓋；query 讀最新一筆。
- **API 整合**：list/detail 回傳的 tier 與 feasibility_score 對齊物化值與當前門檻。

## 8. 推出順序與回退

1. 重構 reasoning（等價）＋ migration（加欄/建表）＋ 物化 job ＋ query 接點（種子門檻）＋ 測試 → commit（Stage 1）。
2. 門檻學習 job ＋ 信心校準 ＋ self_evolve 串接 ＋ 測試 → commit（Stage 2）。

- 回退：刪 `TierThresholdRevision` 全表或不跑 Stage 2 → query 自動回種子 62/42；
  `feasibility_team` 全 NULL → 全面回退報表 tier（等同上線前行為）。零破壞性。
