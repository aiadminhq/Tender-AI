# 02 ｜ 本地端 ↔ 雲端 同步規範

> 先讀 `00-總覽與心智模型.md`。本檔說明「收到本地更新」或「雲端做完要回流」時怎麼辦。
> 核心：雲端與本地**不直接互通檔案，一律透過 GitHub 當中轉站**。

---

## 1. 方向一：本地 → 雲端（你在本機改了東西，要雲端接手）

1. 本地先 `commit` 並 `push` 到一個分支（建議獨立分支，不要直接動別人正在用的分支）。
2. 告知雲端 session：「請以 `<branch>` 為基準」或「請 fetch 並 rebase `<branch>`」。
3. 雲端動作：`git fetch origin <branch>` →（必要時）`git rebase` 或 `git merge` → 確認 build／test 綠燈再繼續。

## 2. 方向二：雲端 → 本地（雲端做完，你要拉回本機）

1. 雲端 push 到指定分支。
2. 本機 `git fetch origin <branch>` → `git pull origin <branch>`（或開 PR 後合併）。

---

## 3. 衝突與覆蓋的鐵則

- **先看再動**：要覆蓋／刪除既有檔案前，先讀內容；若與描述不符，或不是你建立的，**停下來回報**，不要直接蓋。
- **小步快跑**：每個改動小、每步可測、檔案範圍精確；雲端容器沒有可隨意回退的本機歷史。
- **同檔競爭**：若發現別的 session／工具正在改同一檔案，停止而非覆蓋。
- **網路重試**：`push` / `fetch` 失敗若為網路問題，最多重試 4 次（2s→4s→8s→16s）。

---

## 4. 分支與提交規範

### 分支命名
- `claude/<主題>`：AI session 工作分支（現用 `claude/busy-sagan-gm197s`）。
- `feat/<主題>`、`fix/<主題>`、`docs/<主題>`、`chore/<主題>`：一般人類分支。

### Commit 訊息：Conventional Commits + 範圍標籤
```
feat(be): 灌入 Layer A 向量到 pgvector
fix(fe): 修正趨勢圖改接後端後的 loading 狀態
data: 新增 P4 預算門檻特徵
docs: 建立專案開發管理規範
```
範圍標籤：`be`(後端) / `fe`(前端) / `data`(資料/訓練) / `infra`(部署環境) / `docs`(文件)。

### 紅線
- **未經明確同意，不開 Pull Request、不推到非指定分支。**
- push 一律 `git push -u origin <branch>`。
