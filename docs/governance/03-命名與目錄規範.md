# 03 ｜ 命名與目錄規範

> 先讀 `00-總覽與心智模型.md`。
> 目的：讓 AI 在陌生 session 也能靠命名快速定位「領域知識在哪、某功能在哪」；讓人也看得懂。

---

## 1. 既有目錄地圖（請維持，不要散落）

```
tender-ai-backend/
  app/api/v1/      # 對外端點（一個檔一個資源：tenders / search / reasoning ...）
  app/services/    # 商業邏輯（一個檔一個職責）
  app/models/      # 資料表（依 Layer A/B/C 分群，檔頭註明所屬層）
  app/jobs/        # 背景批次工作（backfill / embed / learn_keywords ...）
  app/adapters/    # 對外來源轉接（pcc / tmu），I/O 與解析分離
  knowledge/       # 領域知識文件（會被切塊嵌入，見第 3 節）
  tests/           # 對應 app/ 的測試，檔名 test_<被測模組>.py
tender-ai-frontend/
  src/pages/       # 整頁
  src/components/<功能群>/   # tenders / rules / assistant / push / kanban / dashboard / layout
  src/store/       # 全域狀態（app-context 偏好、app-data 領域資料）
  src/lib/         # 純函式與 API client，必附 *.test.ts
  src/i18n/        # 文案，zh / en 成對
```

---

## 2. 命名約定

- **後端檔案／函式**：`snake_case`；測試一律 `test_<模組>.py`。
- **前端元件**：檔名 `kebab-case.tsx`，元件 `PascalCase`。
- **i18n key**：語意化（如 `assistantPlaceholder`），新增時 **zh／en 必須成對**，繁中為預設語系。
- **資料表**：名稱即用途；Layer B 表的檔頭註明「INTERNAL-SHARED — Layer B，限白名單(@hqdesign.tw)合作範圍共享、依登入帳號具名，對非合作範圍對象永不揭露」。
- **功能代號**：一律用 `00-總覽` 的 SLx / Px / Layer，不得新增同義代號。

---

## 3. 「專業諮詢／領域知識」放哪（AI 取用的來源）

| 內容類型 | 放這裡 |
| --- | --- |
| 領域知識（投標規則、判斷準則、產業 know-how） | `tender-ai-backend/knowledge/*.md`，由 `ingest_knowledge.py` 嵌入成 `knowledge_chunks`，AI 助理（SL1）才取得到 |
| 規格 / 設計決策 | `docs/superpowers/specs/`、`docs/superpowers/plans/` |
| 產品願景 | `PRD.md` |
| 視覺 / 設計系統 | `DESIGN.md`、`tender-ai-design-system.md` |
| 開發治理（本系列） | `docs/governance/` |

> 👉 **新的領域知識請寫成 `knowledge/` 的 Markdown，不要塞進程式碼註解**，否則 AI 助理讀不到、也無法被學習迴圈使用。
